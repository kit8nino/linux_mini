# Пошаговое написание скриптов: три типовые задачи

**Как читать.** Для каждой задачи дан алгоритм создания файла скрипта. Каждый шаг добавляет **одну команду или одну функцию** и объясняет, как она работает. Полный код не приводится — только рамочные фрагменты и описание логики. Ваша задача — собрать скрипт самостоятельно, проверяя результат после каждого шага.

**Общий принцип:** сначала каркас и переменные → потом функции → потом основной блок → потом обработка ошибок и тестирование.

# Задача 1. Скрипт бэкапа папки с ротацией и логированием

**Постановка:** заархивировать указанную папку в `.tar.gz` с датой в имени, удалить бэкапы старше 30 дней, писать всё в лог, корректно завершаться при ошибках.

## Шаг 1. Создать файл и задать шебанг

Создайте файл `backup.sh`. Первая строка — шебанг `#!/bin/bash`. Он говорит ядру, каким интерпретатором запускать файл. Без него скрипт может выполниться другой оболочкой (например, `sh`), и синтаксис Bash сломается.

**Рамочно:**
```bash
#!/bin/bash
```

## Шаг 2. Включить строгий режим

Добавьте `set -euo pipefail`. Эта директива делает три вещи: `-e` — выход при любой ошибке команды; `-u` — выход при обращении к необъявленной переменной; `-o pipefail` — ошибка в любом звене пайпа делает весь пайп ошибочным. Без этого скрипт может «проглотить» сбой и продолжить работу с неверными данными.

**Рамочно:**
```bash
set -euo pipefail
```

## Шаг 3. Определить конфигурационные переменные

В начале скрипта задайте переменные: `SOURCE` (что бэкапим), `BACKUP_DIR` (куда), `RETENTION_DAYS` (сколько дней хранить), `LOG_FILE` (куда писать лог). Для даты используйте командную подстановку `$(date +%Y%m%d_%H%M%S)` — она выполнится в момент запуска и даст уникальное имя архива. Имя файла бэкапа соберите из `BACKUP_DIR` и даты.

**Почему в начале:** все настройки в одном месте — легче менять, не читая весь скрипт.

## Шаг 4. Добавить функцию логирования

Добавьте функцию `log()`. Она должна:
- принимать любое число аргументов через `$*`;
- формировать метку времени через `$(date '+%Y-%m-%d %H:%M:%S')`;
- писать строку одновременно в файл и на экран через `tee -a "$LOG_FILE"`.

**Зачем `tee -a`:** при ручном запуске вы видите, что происходит; при запуске из cron — всё сохраняется в лог.

**Рамочно:**
```bash
log() { ... }
```

## Шаг 5. Добавить функцию аварийного выхода

Добавьте функцию `die()`. Она принимает сообщение и код возврата, пишет сообщение в **stderr** через `>&2` и завершает скрипт через `exit`. Это нужно, чтобы ошибки не терялись среди обычного вывода и чтобы код возврата скрипта был ненулевым — cron и мониторинг это увидят.

**Рамочно:**
```bash
die() { ... }
```

## Шаг 6. Проверить существование источника

В основном блоке первым делом проверьте, что `$SOURCE` существует и является папкой. Используйте `[ -d "$SOURCE" ]` в конструкции `if`. Если проверка не прошла — вызовите `die` с понятным сообщением. Это защита от опечатки в пути: без неё `tar` создаст пустой архив или упадёт с невнятной ошибкой.

**Рамочно:**
```bash
if [ ! -d "$SOURCE" ]; then
    die "..."
fi
```

## Шаг 7. Создать каталог для бэкапов

Убедитесь, что `$BACKUP_DIR` существует. Используйте `mkdir -p "$BACKUP_DIR"` — флаг `-p` создаёт все промежуточные каталоги и не ругается, если каталог уже есть. Это делает скрипт идемпотентным: его можно запускать повторно без ошибок.

## Шаг 8. Создать архив

Вызовите `tar -czf "$BACKUP_FILE" "$SOURCE"`. Флаги: `c` — создать, `z` — сжать gzip, `f` — имя файла. Путь к источнику заключён в кавычки — это защита от пробелов в пути.

После вызова проверьте результат: `[ -s "$BACKUP_FILE" ]` — архив существует и не пустой. Если пустой — вызовите `die`.

**Почему проверять размер:** `tar` может вернуть код 0, но создать пустой файл, если источник исчез между проверкой и архивацией.

## Шаг 9. Добавить ротацию старых бэкапов

Вызовите `find "$BACKUP_DIR" -name "*.tar.gz" -mtime +$RETENTION_DAYS -delete`. `-mtime +N` — файлы старше N дней. Сначала лучше заменить `-delete` на `-print` и убедиться, что находится именно то, что нужно.

**Важно:** `-delete` необратим. Проверка через `-print` — обязательный шаг перед включением удаления.

## Шаг 10. Добавить `trap` для очистки

В начале основного блока создайте временный файл через `mktemp` и зарегистрируйте `trap 'rm -f "$TEMP"' EXIT`. Это гарантирует, что временный файл будет удалён, даже если скрипт упадёт с ошибкой или будет прерван по `Ctrl+C`.

**Зачем:** без `trap` временные файлы накапливаются и засоряют систему.

## Шаг 11. Проверить синтаксис и запустить вручную

Выполните `bash -n backup.sh` — проверка синтаксиса без выполнения. Затем `chmod +x backup.sh` и запустите `./backup.sh`. Посмотрите лог. Затем запустите с `bash -x backup.sh` — увидите каждую команду с подставленными значениями переменных.

## Шаг 12. Добавить в cron (опционально)

Откройте `crontab -e` и добавьте строку запуска, например ежедневно в 3:00. Укажите **абсолютный путь** к скрипту и перенаправьте вывод в отдельный лог cron через `>> /var/log/backup_cron.log 2>&1`. В cron нет вашего `PATH`, поэтому все команды в скрипте должны быть либо с абсолютными путями, либо `PATH` должен быть задан внутри скрипта.

# Задача 2. Скрипт мониторинга сервиса с перезапуском и уведомлением

**Постановка:** каждые N секунд проверять, работает ли сервис. Если нет — перезапустить до M раз. При неудаче — отправить уведомление и записать в лог. Скрипт должен корректно завершаться по сигналу.

## Шаг 1. Создать файл, шебанг и строгий режим

Создайте `monitor.sh`, добавьте `#!/bin/bash` и `set -euo pipefail`. Объяснение то же, что в Задаче 1: строгий режим не даёт скрипту продолжать работу после сбоя.

## Шаг 2. Определить конфигурацию

Задайте переменные: `SERVICE` (имя сервиса), `LOG_FILE`, `CHECK_INTERVAL` (пауза между проверками), `MAX_RETRIES` (сколько попыток перезапуска), `TELEGRAM_TOKEN` и `TELEGRAM_CHAT_ID` (если будете отправлять уведомления). Все настройки — в начале, чтобы не искать их по коду.

## Шаг 3. Добавить функцию логирования

Функция `log()` — как в Задаче 1: метка времени, `tee -a`, произвольное число аргументов. Логирование обязательно: без него вы не узнаете, что скрипт делал ночью.

## Шаг 4. Добавить функцию проверки процесса

Функция `check_process()` принимает имя сервиса и вызывает `pgrep -x "$SERVICE" > /dev/null 2>&1`. Возвращает 0, если процесс найден, и 1, если нет. `-x` — точное совпадение имени, чтобы не поймать `nginx-helper` вместо `nginx`. `> /dev/null 2>&1` скрывает вывод `pgrep`: нам нужен только код возврата.

**Рамочно:**
```bash
check_process() { ... }
```

## Шаг 5. Добавить функцию проверки порта (альтернатива)

Функция `check_port()` принимает хост и порт и вызывает `nc -z "$HOST" "$PORT" 2>/dev/null`. Возвращает 0, если порт открыт. Это надёжнее `pgrep`, если сервис может работать, но не отвечать. Используйте как дополнительную проверку или вместо `pgrep`, если сервис не управляется systemd.

**Рамочно:**
```bash
check_port() { ... }
```

## Шаг 6. Добавить функцию перезапуска с повторами

Функция `restart_service()` должна:
- в цикле `for ((i=1; i<=MAX_RETRIES; i++))` пытаться перезапустить сервис через `systemctl restart "$SERVICE"`, а если systemd нет — через `service "$SERVICE" restart`;
- после каждой попытки ждать `sleep 2` и снова проверять `check_process`;
- при успехе возвращать 0, при исчерпании попыток — 1.

**Почему цикл:** один сбой `systemctl` может быть временным. Повторы повышают шанс восстановления.

## Шаг 7. Добавить функцию уведомления

Функция `notify()` принимает текст и отправляет его во внешний канал (Telegram, Slack, email). Для Telegram используйте `curl` к `https://api.telegram.org/bot$TELEGRAM_TOKEN/sendMessage` с параметрами `chat_id` и `text`. Если внешний канал не настроен — функция должна просто писать в лог и возвращать 0, чтобы скрипт не падал.

**Рамочно:**
```bash
notify() { ... }
```

## Шаг 8. Добавить `trap` для корректного выхода

Зарегистрируйте `trap` на `SIGINT` и `SIGTERM`. В обработчике: записать в лог «получен сигнал, завершаюсь», удалить временные файлы, выйти с кодом 0. Без этого `Ctrl+C` оставит после себя незавершённые операции и временные файлы.

**Рамочно:**
```bash
trap '...' SIGINT SIGTERM
```

## Шаг 9. Написать основной цикл

Основной блок — `while true`. Внутри:
1. Вызвать `check_process` (и/или `check_port`).
2. Если всё хорошо — залогировать «OK» и перейти к `sleep`.
3. Если плохо — залогировать «FAIL», вызвать `restart_service`.
4. Если перезапуск не удался — вызвать `notify` и залогировать критическую ошибку.
5. В конце итерации — `sleep "$CHECK_INTERVAL"`.

**Почему `while true`:** скрипт работает как демон и проверяет сервис постоянно. Выход — только по сигналу или если вы явно добавите условие `break`.

## Шаг 10. Проверить синтаксис и запустить вручную

`bash -n monitor.sh` — проверка синтаксиса. Затем запустите `./monitor.sh` в отдельном терминале. Остановите тестовый сервис (например, `sleep`-процесс) и убедитесь, что скрипт его перезапускает и пишет в лог.

## Шаг 11. Запустить как демон

Варианты:
- `nohup ./monitor.sh &` — простой фоновый запуск, вывод в `nohup.out`.
- `tmux new -s monitor` и запуск внутри — правильный способ для интерактивного наблюдения.
- `cron` с запуском раз в минуту — если скрипт не должен работать постоянно, а проверять по расписанию.

**Важно:** если запускаете через cron, скрипт должен завершаться после одной проверки. Для этого уберите `while true` или добавьте флаг `--once`.

# Задача 3. Скрипт пакетной обработки файлов с отчётом

**Постановка:** рекурсивно найти файлы по маске и возрасту, выполнить над каждым действие (например, сжать `gzip`), вести отчёт: сколько найдено, сколько обработано, сколько пропущено. Поддержать режим dry-run.

## Шаг 1. Создать файл, шебанг и строгий режим

Создайте `batch.sh`, добавьте `#!/bin/bash` и `set -euo pipefail`. Как в предыдущих задачах.

## Шаг 2. Определить конфигурацию

Задайте переменные: `TARGET_DIR` (где искать), `MASK` (например, `*.log`), `MIN_AGE_DAYS` (возраст файла), `LOG_FILE`, `DRY_RUN` (0/1). `DRY_RUN` можно выставлять через аргумент командной строки или переменную окружения.

## Шаг 3. Добавить функцию логирования

`log()` — стандартная: метка времени, `tee -a`, произвольные аргументы. Без лога вы не поймёте, что произошло с каждым файлом.

## Шаг 4. Разобрать аргументы командной строки

Добавьте разбор `$1` через `case`: `--dry-run` выставляет `DRY_RUN=1`, `--help` печатает справку и выходит, неизвестный аргумент — вызывает ошибку через `>&2` и `exit 1`. Это делает скрипт удобным и безопасным: пользователь явно выбирает режим.

**Рамочно:**
```bash
case "${1-}" in
    --dry-run) ... ;;
    --help|-h) ... ;;
    *) ... ;;
esac
```

## Шаг 5. Добавить функцию проверки входных данных

Функция `validate()` проверяет, что `TARGET_DIR` существует (`[ -d ]`), что `MASK` не пустая (`[ -n ]`), что `MIN_AGE_DAYS` — число. При ошибке — вызов `die` с понятным сообщением. Это отсекает опечатки до начала обработки.

**Рамочно:**
```bash
validate() { ... }
```

## Шаг 6. Добавить функцию обработки одного файла

Функция `process_file()` принимает путь к файлу и:
- проверяет, не обработан ли он уже (например, существует ли `"$file.gz"` рядом);
- если `DRY_RUN=1` — только логирует «был бы обработан» и возвращает 0;
- иначе выполняет действие (`gzip "$file"`), проверяет код возврата и логирует результат.

**Почему отдельная функция:** логика обработки одного файла не должна смешиваться с обходом каталога. Так проще тестировать и менять.

**Рамочно:**
```bash
process_file() { ... }
```

## Шаг 7. Добавить функцию обхода файлов

Функция `walk_files()` вызывает `find "$TARGET_DIR" -type f -name "$MASK" -mtime +"$MIN_AGE_DAYS" -print0` и передаёт результат в `while IFS= read -r -d '' file`. Внутри цикла вызывает `process_file "$file"` и обновляет счётчики: `found`, `processed`, `skipped`, `errors`.

**Почему `-print0` и `read -d ''`:** это единственный безопасный способ обработать имена с пробелами и переводами строк. Обычный `for file in $(find ...)` сломается на пробелах.

**Рамочно:**
```bash
walk_files() { ... }
```

## Шаг 8. Добавить счётчики и итоговый отчёт

Внутри `walk_files` заведите переменные `found=0`, `processed=0`, `skipped=0`, `errors=0`. После цикла вызовите `log` с итоговой сводкой. Если `errors > 0` — завершите скрипт с ненулевым кодом через `exit 1`, чтобы cron или мониторинг увидели проблему.

**Почему счётчики:** без них вы не узнаете, сколько файлов реально обработано, а сколько пропущено. Это важно для аудита.

## Шаг 9. Добавить `trap` для очистки

Если скрипт создаёт временные файлы (например, список найденных файлов), зарегистрируйте `trap 'rm -f "$TEMP"' EXIT`. Это гарантирует очистку при любом исходе.

**Рамочно:**
```bash
trap '...' EXIT
```

## Шаг 10. Собрать основной блок

В основном блоке:
1. Вызвать `validate`.
2. Залогировать старт с параметрами (`TARGET_DIR`, `MASK`, `MIN_AGE_DAYS`, `DRY_RUN`).
3. Вызвать `walk_files`.
4. Залогировать завершение.
5. Вернуть код 0 при успехе или 1 при ошибках.

**Почему так:** основной блок должен быть коротким и читаемым. Вся логика — в функциях.

## Шаг 11. Проверить синтаксис и запустить в dry-run

`bash -n batch.sh` — проверка синтаксиса. Затем `./batch.sh --dry-run` — вы увидите, что **было бы** сделано, без реальных изменений. Убедитесь, что находятся нужные файлы и пропускаются уже обработанные.

## Шаг 12. Запустить в боевом режиме и проверить отчёт

Запустите без `--dry-run`. Проверьте: файлы сжаты, появились `.gz`, в логе есть итоговая сводка. Запустите повторно — скрипт должен пропустить уже обработанные файлы и записать `skipped > 0`.

## Шаг 13. Добавить в cron (опционально)

Добавьте запуск в `crontab -e`, например раз в день. Укажите абсолютный путь к скрипту и режим `--dry-run` на первых запусках, чтобы убедиться, что находится именно то, что нужно. После проверки уберите `--dry-run`.

# Общие правила написания скриптов (чек-лист)

1. **Шебанг** — `#!/bin/bash` или `#!/usr/bin/env bash`.
2. **Строгий режим** — `set -euo pipefail`.
3. **Конфигурация** — все переменные в начале.
4. **Функции** — логирование, ошибки, проверки, обработка, обход.
5. **Основной блок** — короткий, только вызовы функций.
6. **Обработка ошибок** — `die`, `trap`, ненулевой `exit` при сбое.
7. **Dry-run** — для опасных операций.
8. **Отладка** — `bash -n` и `bash -x`.
9. **Логирование** — всё важное в лог, ошибки в `>&2`.
10. **Cron-совместимость** — абсолютные пути, `PATH` внутри скрипта.
