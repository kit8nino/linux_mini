
**Цель блока:** Научиться видеть, что происходит в системе в реальном времени, понимать иерархию процессов, грамотно завершать зависшие приложения и запускать фоновые задачи, не боясь, что они умрут при закрытии терминала.

## 5.1. Что такое процесс и PID (Process ID)

Программа (исполняемый файл на диске) — это пассивный набор инструкций. Когда вы запускаете программу, она становится **процессом** — активной сущностью в памяти, которой ядро выделяет ресурсы (CPU, RAM).

- **PID (Process ID)** — уникальный номер процесса. Как паспорт.
- **PPID (Parent Process ID)** — номер родительского процесса. Кто породил этот процесс.

**Иерархия:** Когда система загружается, первым стартует `init` (или `systemd`) с PID=1. Это «прародитель» всех процессов. Если вы запускаете команду из Bash, Bash становится родителем (PPID) для этой команды.

## 5.2. Статические «снимки» процессов: `ps`

Команда `ps` (Process Status) показывает состояние процессов *на момент запуска команды*. Она не обновляется.

**Существует два стиля флагов (старый Unix и BSD). Запомните два самых полезных набора:**

**1. `ps aux` (Стандарт BSD) — используйте его на 90% случаев.**
Выдает все процессы системы в удобном формате.

```bash
ps aux
```
**Разбор колонок (самое важное):**

| Колонка    | Что означает                           | На что обращать внимание                                 |
| :--------- | :------------------------------------- | :------------------------------------------------------- |
| `USER`     | Владелец процесса.                     | Кто запустил. Если это `root` — процесс системный.       |
| `PID`      | Идентификатор.                         | Нужен для убийства (`kill`).                             |
| `%CPU`     | Использование процессора в процентах.  | Если > 100% (на многоядерных) — процесс грузит систему.  |
| `%MEM`     | Использование оперативной памяти.      | Если высокий — возможно, утечка памяти.                  |
| `VSZ`      | Виртуальная память (всего выделено).   | Не очень информативно.                                   |
| `RSS`      | Резидентная память (фактически в ОЗУ). | На что смотреть.                                         |
| **`STAT`** | **Состояние процесса.**                | **Это важно!** Смотрите ниже.                            |
| `TIME`     | Время использования CPU.               | Если процесс работает сутки, а `TIME` = 0:00 — он висит. |
| `COMMAND`  | Сама команда с аргументами.            | Ищем по имени.                                           |

**2. `ps -ef` (Стандарт System V)**
Выдает полный список со строгой структурой колонок. Полезен, если нужно увидеть PPID (родителя) четко: `ps -ef | grep nginx`.

**Дерево процессов:**
`ps auxf` (с флагом `f` — forest) — показывает иерархию в виде ASCII-дерева. Отлично видно, кто кого запустил.

## 5.3. Статусы процессов (STAT) — как понять, что процесс «висит»

В колонке `STAT` вы увидите буквы. Запомните 5 критических:

| Буква | Состояние | Расшифровка |
| :--- | :--- | :--- |
| **R** | Running | Процесс **выполняется** прямо сейчас или стоит в очереди на CPU. |
| **S** | Sleeping | Процесс **спит** (ожидает события, ввод/вывод). Это нормально. |
| **D** | Uninterruptible Sleep | Процесс ждет диск или сеть и *не может быть прерван*. Если их много — проблемы с диском. |
| **Z** | Zombie | Процесс завершился, но родитель не прочитал его статус. «Мертвая душа». Не потребляет ресурсы, но мешает. Исчезает, если убить родителя. |
| **T** | Stopped | Процесс остановлен (обычно по `Ctrl+Z`). |

## 5.4. Интерактивный мониторинг: `top` и `htop`

Это «Диспетчер задач» в консоли. В отличие от `ps`, данные обновляются каждые 2-3 секунды.

**Классический `top`:**
Запустите `top`. Сверху вы видите общую нагрузку (load average), количество процессов, использование памяти. Снизу — список.
**Горячие клавиши внутри `top` (выучите!):**

- `P` — отсортировать процессы по **CPU** (самые жирные сверху).
- `M` — отсортировать по **памяти** (RAM).
- `k` — убить процесс (запросит PID и сигнал).
- `r` — изменить приоритет (renice) процесса.
- `q` — выход.

**Продвинутый `htop` (установите его первым делом):**
`sudo apt install htop` / `sudo yum install htop`.
Он цветной, показывает дерево (`F5`), умеет убивать процессы стрелками без ввода PID (`F9`), и видит все ядра CPU сразу. Для стажера `htop` — спасение.

## 5.5. Управление сигналами: `kill`, `killall`, `pkill`

Процессы в Linux общаются с ядром через **сигналы**. Это как сообщения: «закройся», «перечитай конфиг», «умри немедленно».

**Основной инструмент — `kill`**. Но это не значит «убить»; это значит «отправить сигнал».

**Синтаксис:** `kill -[Сигнал] [PID]`

Сначала посмотрим список сигналов: `kill -l` (их много, но нам нужно 3).

| Сигнал | Номер | Эффект | Когда использовать |
| :--- | :--- | :--- | :--- |
| **SIGTERM** | **15** | Вежливое завершение. Отправляет процессу команду «закрой файлы, освободи ресурсы и выйди». | **По умолчанию** (`kill 1234`). Всегда используйте его сначала. |
| **SIGKILL** | **9** | Беспощадное убийство. Ядро просто вырезает процесс из памяти. Процесс не может его игнорировать. | Если SIGTERM не помог (процесс висит в статусе D или игнорирует 15-й сигнал). Крайняя мера. |
| **SIGHUP** | **1** | «Перечитать конфигурацию». Многие сервисы (nginx, sshd) при получении этого сигнала перезагружают свои настройки без остановки. | `kill -1 [PID_nginx]` — применить новый конфиг без даунтайма. |

**Массовое убийство по имени:**

- `killall nginx` — отправить SIGTERM всем процессам с именем nginx.
- `killall -9 python` — жестко убить все Python-скрипты.
- `pkill -f "my_script.py"` — убить по части имени команды. (`-f` ищет по полной командной строке).

**Предупреждение:** Никогда не убивайте процессы с PID 1 (systemd) или PID вашего SSH-демона, пока вы зашли по SSH — потеряете связь с сервером.

## 5.6. Приоритеты процессов (Nice)

Процессор не резиновый. У каждого процесса есть «вежливость» (Nice value) от -20 (самый высокий приоритет) до +19 (самый низкий).

- Запустить процесс с низким приоритетом (чтобы не мешал системе): `nice -n 10 ./heavy_script.sh`
- Изменить приоритет у работающего процесса: `renice -n 5 -p 1234` (PID 1234 теперь будет крутиться в фоне, уступая ресурсы).
- В `htop` можно менять приоритет нажатием `F7` (увеличить приоритет) и `F8` (уменьшить).

## 5.7. Фоновые задачи и их жизнь: `&`, `jobs`, `fg`, `bg`

Когда вы запускаете команду, терминал блокируется до её завершения. Чтобы освободить терминал:

1.  **Запустить в фоне сразу:** `ping google.com &` (команда выполняется, а терминал свободен).
2.  **Приостановить работающую:** Нажмите `Ctrl + Z` — процесс перейдет в статус `T` (Stopped) и скроется в фоне.

**Управление фоновыми задачами (внутри одного терминала):**
- `jobs` — показать список задач, запущенных в этом терминале (с номерами `[1]`, `[2]`).
- `fg %1` — вернуть задачу №1 на передний план (foreground).
- `bg %2` — продолжить выполнение задачи №2 в фоне (background), чтобы она работала, пока вы делаете что-то другое.

## 5.8. Демоны и проблема SIGHUP

Закройте терминал — все дочерние процессы (запущенные из этого терминала) получат сигнал **SIGHUP** (сигнал «повисла трубка») и умрут.

**Как запустить процесс, чтобы он жил вечно, даже если вы вышли из системы?**

**Способ 1 (базовый): `nohup` (No Hang Up)**
`nohup ./my_script.sh &`
Выходные данные будут записаны в файл `nohup.out` в текущей папке. Процесс игнорирует SIGHUP.

**Способ 2 (Правильный, профессиональный): Терминальные мультиплексоры.**

- **`screen`** или **`tmux`**. Это «виртуальные терминалы», которые живут отдельно от вашего подключения.
- Запускаете `tmux`, внутри него скрипт. Закрываете SSH-сессию. Через час заходите снова, подключаетесь к тому же `tmux` и видите, что скрипт всё еще работает, а вывод вы можете продолжать смотреть.
- *Правило хорошего тона:* Для долгих миграций баз данных или скачивания больших файлов используйте только `tmux` или `screen`.

## 5.9. Боевые сценарии (Применяем на практике)

| Ситуация | Действие |
| :--- | :--- |
| **Сервер тормозит, CPU забит.** | Запусти `htop`, нажми `P` (сортировка по CPU). Найди жирный процесс. Нажми `F9` -> `15` (SIGTERM) -> Enter. Не помогло? Еще раз `F9` -> `9` (SIGKILL). |
| **Nginx не подхватывает новый конфиг.** | Проверь синтаксис (`nginx -t`). Если ок — `kill -1 [PID_master_nginx]`. Он перечитает конфиг без потери соединений. |
| **Зависла программа, которая пишет лог, не могу её остановить.** | Попробуй `kill -15 [PID]`. Если висит в статусе `D` (ждать диск) — убить её сложно, придется ждать или перезагружать ОС. |
| **Запустил скрипт, а он будет выполняться 3 часа, а мне пора домой.** | Нажми `Ctrl+Z` (приостановить). Выполни `bg` (запустить в фоне). Выполни `disown -h %1` (отвязать задачу от терминала). Теперь можно закрывать терминал — процесс не умрет. |

**Задание для самопроверки к Блоку 5:**

1.  Запустите в терминале команду `sleep 300`.
2.  Нажмите `Ctrl + Z`, чтобы приостановить её.
3.  Введите `jobs` — убедитесь, что задача висит.
4.  Введите `bg` — продолжите задачу в фоне.
5.  Найдите PID этого процесса через `ps aux | grep sleep`.
6.  Убейте его командой `kill` (используя найденный PID).
7.  Проверьте через `ps aux | grep sleep` — процесса больше нет.
8.  (Дополнительно) Найдите PID вашего терминала (Bash) через `echo $$`. Убейте его через `kill -9` и посмотрите, что случится с терминалом (он закроется — делайте это только в тестовой среде, если не жалко).
